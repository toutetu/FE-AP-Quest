# FE-AP-Quest Constitution

## Core Principles

### I. 合格ファースト

- すべての機能は「2026年12月までに応用情報（AP）と基本情報（FE）に合格する」ことに
  役立つものでなければならない（MUST）。
- ゲームの要素は勉強を続けるための仕掛けであり、勉強そのものを置き換えてはならない（MUST NOT）。
- 試験日（AP科目A 〜11/10、AP科目B 〜12/6、FE 〜12/27）に間に合わない機能は、
  次の段階へ回す。
- 理由: 試験日は動かせず、アプリを作ること自体が目的になるのを防ぐため。

### II. 毎日続く・すぐ使える

- 調べたことのメモは、スマホ片手で10秒以内に登録できなければならない（MUST）。
- アプリを開いたら、最初の画面で「今日やること」がわかる（MUST）。
- 面接・面談などで忙しい日でも、こなせる最低限のノルマを必ず示す（MUST）。
- 理由: 就活などの予定で時間が細切れになるため、手間が増えると使われなくなる。

### III. プライバシーを守る設計

- カレンダー・メールの中身を、リポジトリ・ソースコード・公開されるファイルに
  含めてはならない（MUST NOT）。
- 予定は、アプリを開いたときに利用者本人の権限で読み、使うのは
  「就活の予定があるか」「空いている時間帯」など必要最小限に限る（MUST）。
- 認証情報・APIキー・個人情報をリポジトリに入れてはならない（MUST NOT）。
- 理由: リポジトリは就活のために公開する。

### IV. 仕様が先、小さく出す

- すべての機能は Spec Kit の仕様（spec）→ 計画（plan）→ タスク（tasks）を経てから作る（MUST）。
- 各段階（第1弾・第2弾…）は、それだけで使える状態で出す（MUST）。
- 仕様はオーナーが確認してから計画に進む（MUST）。
- 理由: 要件定義から作った過程そのものを、就活で説明できる実績にするため。

### V. 学習ロジックはテストで守る

- 復習の出題日の計算、ノルマの計算、擬似言語の実行など、学習の中身を決める処理は
  画面から切り離し、自動テストを付けなければならない（MUST）。
- 画面の見た目は、スマホ幅とPC幅での手動確認でよい。
- 理由: 復習日がずれると、気づかないうちに学習効果が落ちるため。

### VI. AIの答えは疑える形で出す

- AIが作った解説・問題・添削には、AIが作ったものであることを表示する（MUST）。
- 利用者がAIの内容を修正・削除できる（MUST）。
- 試験制度や日程は、IPAの公式情報を出典として示す（SHOULD）。
- 理由: AIは間違えることがあり、誤った知識を覚えると試験で失点するため。

## 技術上の制約

- 言語は TypeScript を使う。
- アプリは claude.ai の非公開ページ（Artifact）として公開し、スマホとPCで同じURLから使う。
- 記録の保存、AIの呼び出し、カレンダーの読み取りは claude.ai のページの機能を使い、
  自前のサーバーやAPIキーを持たない。
- 画面は日本語。スマホ幅（375px）とPC幅の両方で使えること。
- ソースコードは GitHub の公開リポジトリで管理する。

## 開発の進め方

- 実装は Claude Code が行い、オーナーは仕様を決め、動作を確認し、直したい点を伝える。
- 開発の時間は1日1時間を目安とし、勉強と就活の時間を削らない。
- 機能ごとにブランチを作り、`specs/` に仕様・計画・タスクを残す。
- README は日本語で書き、就活で見せられるよう、作った理由・工夫・使った技術を載せる。

## Governance

- この憲法は、このリポジトリのほかの決まりごとより優先する。
- 変更はオーナー（toutetu）が承認し、変更理由をこのファイルに記録する。
- バージョンは次のように上げる: 原則の削除や意味の変更は MAJOR、原則や節の追加は MINOR、
  言い回しの修正は PATCH。
- 仕様・計画を作るときは、この憲法に反していないかを確認する。
