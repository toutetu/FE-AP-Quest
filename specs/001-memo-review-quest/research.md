# Research: 第1弾 メモ・復習・クエスト

Phase 0 の調査結果。各項目は「決定・理由・ほかに検討した案」の順に書く。
Technical Context に「要確認」は残っていない。

## R1. 画面を作る仕組み

- **Decision**: React 18.3.1 を使い、cdnjs の UMD 版（`react.production.min.js` と
  `react-dom.production.min.js`）をページから読み込む。ビルド時は `react` / `react-dom` を外部扱いにし、
  JSX は `React.createElement` に変換する（クラシック形式）。
- **Rationale**: Artifact のページ規約では、ライブラリは cdnjs などの許可されたCDNから、バージョンを固定した
  UMD版を読み込むことが推奨されている。React 19 には UMD 版がないため 18.3.1 を選ぶ（cdnjs で配信を確認済み）。
  React は国内のIT企業の求人で使われることが多く、就活で説明しやすい。
- **Alternatives considered**:
  - React 19 をページに同梱する: 動くがページが大きくなり、規約の推奨から外れる。
  - Preact: 小さく速いが、就活で伝わりやすさが React に劣る。
  - 素の TypeScript（ライブラリなし）: 画面が7つあり、状態の管理を自前で書く量が多い。

## R2. ビルドと公開の形

- **Decision**: Vite 8 と TypeScript 7 でビルドし、vite-plugin-singlefile で JavaScript と CSS を1つの
  HTMLにまとめる。出力は即時実行形式（IIFE）にする。最後に `scripts/build-artifact.mjs` で
  `<!doctype>`・`<html>`・`<head>`・`<body>` を取り除き、`<title>`・Google Fonts の `<link>`・`<style>`・
  React の `<script src>`・アプリの `<script>` を並べた Artifact 用のファイル（`artifact/index.html`）を作る。
- **Rationale**: Artifact は公開時にページを `<!doctype html>…<body>` の枠で包むため、ページ側は中身だけを書く
  決まりがある。1ファイルにすると公開の手順が単純になり、許可されていない場所から何かを読み込む事故も防げる。
- **Alternatives considered**:
  - 複数ファイルで公開する（`files` で JS と CSS を別に送る）: 可能だが、公開のたびに複数ファイルの対応を
    管理する必要がある。
  - ビルドせずに1つのHTMLを手書きする: TypeScript とテストが使えない。

## R3. 記録の保存先

- **Decision**: Artifact の `db` を使い、すべての記録を本人だけが読める `data/users/<id>/` 以下に置く。
  `<id>` は `user` ケーパビリティの `id()` で得る。構成は次のとおり（詳細は data-model.md）。
  - `data/users/<id>/profile` … 設定・ボス・タイマー（1件）
  - `data/users/<id>/profile/memos/<memoId>` … メモ（1件ずつ）
  - `data/users/<id>/profile/studyLogs/<logId>` … 勉強時間と過去問道場の記録（1回ずつ）
- **Rationale**: `data/users/<id>/` は、ページを誰かと共有しても本人以外には見えない。メモを1件ずつ
  別の文書にすると、1文書256KiBの上限に当たらない。メモが3,000件、勉強の記録が数百件でも、
  1つのページあたり25,000件の上限に十分収まる。
- **Alternatives considered**:
  - 共有の場所に置き、書き込みを所有者だけに制限する: 共有設定を変えたときに中身が見えてしまう。
  - 全メモを1つの文書にまとめる: すぐに256KiBの上限に当たる。

## R4. 端末間の同期と、通信がないときの保存

- **Decision**: メモと記録は `onSnapshot` で購読し、どの端末で保存しても次に開いたとき（開いている間は
  すぐに）反映する。保存は、まず端末の `localStorage` の「送信待ち」に入れてから `db` に書き込み、成功したら
  送信待ちから消す。起動時と通信の回復時に、送信待ちを再送する。メモの id は端末側で先に決めるので、
  再送しても重複しない。あわせて、前回の表示内容を `localStorage` に保存し、`db` の返事を待たずに
  ホームを表示する。
- **Rationale**: `db` は書き込みをすぐ画面に反映するが、通信がないままページを閉じると書き込みが失われうる。
  FR-005（通信がないときも失わない）と SC-002（3秒以内に表示）を満たすため。`localStorage` は
  使えない環境もあるので、すべての読み書きを try/catch で包み、使えないときは `db` だけで動かす。
- **Alternatives considered**: IndexedDB は容量が大きいが、送信待ち数件と表示用キャッシュには過剰。

## R5. 経験値・連続日数などの「数」の持ち方

- **Decision**: 経験値、レベル、連続日数、その日の復習数、クエストの達成状況は保存しない。メモ
  （登録日と復習の履歴）と勉強の記録から、毎回計算して求める。
- **Rationale**: `db` の書き込みは「最後に書いたほうが勝つ」方式で、読んで足して書き戻す数え方は、
  2つの端末からほぼ同時に書いたときに数がずれる（db の仕様書でも避けるよう書かれている）。履歴から計算すれば
  ずれようがなく、計算は純粋関数としてテストできる。メモを削除すると、そのメモの分の経験値も減るが、
  記録と表示が常に一致するほうを優先する。
- **Alternatives considered**: 日ごとの集計文書に数を足していく: 書き込みが単純だが、食い違いが起きうる。

## R6. AIチェック

- **Decision**: `sample.json` を、利用者が「AIチェック」を押したときだけ1回呼ぶ。1回の呼び出しで、
  説明の判定・ひっかけポイント・関連用語・分野の提案・復習用の問題（4択または穴埋め）をまとめて返させる。
  モデルは `default`（標準）を使う。返答は項目ごとに検査し、形が合わない項目は捨てる。結果には
  「AIが作成」の印を付けて保存し、説明の修正案は利用者が「採用」を押したときだけメモに反映する。
  指示文と返答の形は [contracts/ai-check.md](./contracts/ai-check.md)。
- **Rationale**: AIの利用は利用者のプランの利用量を使うため、自動では呼ばない（FR-018）。項目ごとに呼ぶと
  回数が増えるので1回にまとめる。試験の知識の正確さが大事なので、速さ重視の `quick` は使わない。
- **エラーの扱い**: `not_granted`・`sampling_disabled` などは AIチェックのボタンを隠す。`rate_limited` は
  「しばらく待ってからもう一度」と伝える。`invalid_json` と `upstream_error` は「もう一度」ボタンを出す。
  どの場合もメモの保存と復習には影響させない（FR-021）。
- **Alternatives considered**: 項目ごとに分けて呼ぶ（回数が増える）、`quick` を使う（正確さに不安）。

## R7. Googleカレンダーの読み取り

- **Decision**: `mcp` ケーパビリティで「Google Calendar」コネクタの `list_events` を呼び、今週
  （月曜4:00〜翌週月曜4:00）の予定を取得する。読むカレンダーは設定画面で `list_calendars` から選び、
  その id は本人の非公開領域（profile）にだけ保存する。結果は5分間キャッシュし、ホームの「更新」で
  取り直す。予定の中身は保存しない（FR-026）。呼び出し方と変換は
  [contracts/calendar.md](./contracts/calendar.md)。
- **Rationale**: 今週の予定がわかれば、今日の判定・スキマ時間・週の割り振り直しがすべて計算できる。
  取得した予定の形（`events[]` の `summary`・`start`・`end`）は、このセッションでの実際の呼び出しで確認した。
- **エラーの扱い**: `needs_reauth` と `server_not_connected` は「claude.ai の設定でGoogleカレンダーを
  つなぎ直してください」と表示し、通常のノルマで動かす。`not_in_manifest`（利用者が許可しなかった）は
  「カレンダーを使わない」状態として扱い、何度も聞かない。`server_unavailable` は1回だけ少し待って
  取り直す。
- **Alternatives considered**: `watchTool` で常に最新に保つ（予定は頻繁に変わらず、5分キャッシュと更新ボタンで
  十分）、すべてのカレンダーを読む（家族の予定なども含まれ、プライバシーの面で不要に広い）。

## R8. 日付の扱い

- **Decision**: 「学習日」は、端末の現地時刻から4時間引いた日付（`YYYY-MM-DD`）とする。週は月曜始まり。
  日付計算はすべて `now` を引数で受け取る純粋関数にし、日付ライブラリは使わない。
- **Rationale**: 夜遅くの勉強を前日に数えるため（仕様のエッジケース）。`now` を外から渡すと、
  「3日後」「月曜の4時直前」などをテストで再現できる。
- **Alternatives considered**: date-fns などのライブラリ（今回必要な計算は少なく、依存を増やすほどではない）。

## R9. 間隔反復の方式

- **Decision**: 間隔の段階を `[1, 3, 7, 14, 30, 60]` 日とし、メモは今の段階（0〜5）と次の出題日を持つ。
  - 新しいメモ: 段階0、出題日は登録の翌日
  - 「覚えてた」: 段階を1つ進め（最大5）、今日からその段階の日数後に出題
  - 「あやしい」: 段階はそのまま、今日からその段階の日数後に出題
  - 「忘れた」: 段階0に戻し、翌日に出題
  - 段階5（60日）に達したメモは「討伐済み」と表示する
- **Rationale**: 仕様（ストーリー2）がこの間隔を指定している。段階だけで状態が決まるので、テストしやすい。
- **Alternatives considered**: SM-2 方式（覚えやすさの係数を持つ。仕様の固定の間隔と合わず、説明もしにくい）。

## R10. 今日の復習の決め方

- **Decision**: 出題日が今日以前のメモを、出題日の古い順（同じなら登録の古い順）に並べ、先頭50件を
  今日の復習にする。51件目以降は自然に翌日以降へ繰り越される。
- **Rationale**: 仕様のエッジケース（溜まりすぎたときは1日50件まで）と FR-008 を満たし、
  古いものから取りこぼさない（SC-003）。

## R11. ノルマの割り振り直し

- **Decision**: 1日の目標を d（新しいメモ5件、過去問道場20問）、今週の就活の日の数を J とする。
  - 就活の日: 目標は「今日の復習を全部」だけ
  - 就活のない日: d + 切り上げ(d × J ÷ (7 − J))
  - 7日すべてが就活の日なら、追加の目標は出さない
  ウィークリーの勉強時間（初期値24時間）は就活の日があっても変えない。
- **Rationale**: 「週の合計目標は変えず、就活のない日のノルマが増える」（ストーリー5）をそのまま式にした。
  過ぎた日の取りこぼしまで上乗せすると負担が膨らむため、上乗せは就活の日の分だけにする。
- **Alternatives considered**: 今週の残りを残りの日数で割る（休んだ日の分まで翌日に乗り、続かなくなる）。

## R12. 就活の日の判定とスキマ時間

- **Decision**:
  - 判定: 予定名を NFKC で正規化し、キーワード（初期値「面接」「面談」「選考」「説明会」）のどれかを含む
    予定がある学習日を就活の日とする。「【仮】」付きの予定も同じ扱い。利用者はその日の判定を手動で
    切り替えられ、その切り替え（日付と真偽だけ）は profile に保存する。
  - スキマ時間: その日の 8:00〜23:00（設定で変更可）のうち、終日の予定を除くすべての予定と重ならない
    30分以上の時間帯。今が範囲内なら今から数える。長さに応じて、30〜59分は「復習」、60〜239分は
    「過去問道場20問＋復習」、240分以上は「過去問道場40問＋苦手な分野の復習」をすすめる
    （仕様のストーリー5の例「3時間: 過去問道場で20問＋復習」に合わせた区切り）。
- **Rationale**: 予定名にキーワードがあれば判定できることを、実際のカレンダーで確かめた。食事や通院などの
  予定もスキマ時間の計算には必要なので、判定とは別に扱う。

## R13. 分野の分け方

- **Decision**: IPA の出題範囲の大分類9・中分類23を使う。ワールドマップは、ストラテジ・マネジメント・
  テクノロジの3つの大陸に、大分類ごとにまとめた中分類23の地方を並べる。
  - テクノロジ系: 基礎理論（基礎理論／アルゴリズムとプログラミング）、コンピュータシステム
    （コンピュータ構成要素／システム構成要素／ソフトウェア／ハードウェア）、技術要素
    （ヒューマンインタフェース／マルチメディア／データベース／ネットワーク／セキュリティ）、開発技術
    （システム開発技術／ソフトウェア開発管理技術）
  - マネジメント系: プロジェクトマネジメント（プロジェクトマネジメント）、サービスマネジメント
    （サービスマネジメント／システム監査）
  - ストラテジ系: システム戦略（システム戦略／システム企画）、経営戦略（経営戦略マネジメント／
    技術戦略マネジメント／ビジネスインダストリ）、企業と法務（企業活動／法務）
- **地方の状態**: その中分類のメモが3件未満なら「霧」。10件以上あり、直近30日の復習で「覚えてた」の割合が
  80%以上なら「制覇」。それ以外は「攻略中」。
- **Rationale**: AP と FE で同じ分け方を使えて、過去問道場の分野とも対応する。

## R14. 経験値・レベル・称号・連続日数

- **Decision**:
  - 経験値: メモ登録 5、復習の回答 2（「覚えてた」は 3）、過去問道場1問 1、勉強10分ごとに 2、
    デイリークエスト達成 30、ウィークリークエスト達成 150。AIチェックには経験値を付けない
    （利用量を使う操作を促さないため）。
  - レベル: レベル L に必要な累計経験値を 25 × L × (L − 1) とする（L2=50、L5=500、L10=2,250、L20=9,500）。
  - 称号: L1 見習い冒険者、L5 用語ハンター、L10 ITパスポーター、L15 基本情報の騎士、
    L20 応用情報の賢者、L30 情報処理の大賢者。
  - 連続日数: 「その日の復習を全部終え、かつ何か1つでも勉強の記録がある日」が何日続いているか。
    今日がまだ条件を満たしていなくても、昨日までの連続は途切れていない扱いにする。
- **Rationale**: 1日に新しいメモ5件・復習30件・過去問道場20問・3.5時間ほどで約200の経験値になり、
  12月までにレベル20台に届く見込み。目標の称号が試験の進み具合と重なるようにした。

## R15. 見た目の方針

- **Decision**: 見出しにドット絵風の日本語フォント（DotGothic16）、本文に読みやすさを重視したUDフォント
  （BIZ UDPGothic）を Google Fonts から読み込み、代わりのフォントも指定する。色はトークンで定義し、
  ライト・ダークの両方を用意する。モンスターは分野ごとに色を変えた小さなドット絵を、ページの中に
  画像データとして埋め込む（外部の画像は読み込めないため）。効果音は利用者が操作したあとにだけ鳴らし、
  設定で消せるようにする。
- **Rationale**: ゲームらしさと、勉強の文字の読みやすさを両立するため。

## R16. 画面の切り替え

- **Decision**: `#home`・`#memo`・`#review`・`#zukan`・`#map`・`#import`・`#settings` の
  記号だけのアンカーで画面を切り替える（[contracts/screens.md](./contracts/screens.md)）。
- **Rationale**: Artifact のリンクで届くのは、英数字だけのアンカーに限られるため。

## R17. テストと開発環境

- **Decision**: `src/domain/` のすべての関数に Vitest のテストを書く。開発中は `npm run dev` で、
  `window.claude` がないときに開発用のつなぎ口（localStorage・ダミーのAI・ダミーの予定）に切り替えて動かす。
  ダミーのデータには「サンプル」と表示する。
- **Rationale**: claude.ai に公開しなくても画面を確認でき、第2弾のデモ版（本人のデータを使わない版）の
  土台にもなる。

## R18. 公開の手順

- **Decision**: `npm run build:artifact` で `artifact/index.html` を作り、Claude Code の Artifact ツールで
  公開する。宣言するケーパビリティは次のとおり。
  `{ db: {}, user: {}, sample: {}, mcp: { servers: [{ server: "Google Calendar", tools: ["list_calendars", "list_events"] }] } }`
  公開後に1回だけ、保存されたデータを読み出して動作を確かめる。ビルド結果（`dist/`・`artifact/`）は
  リポジトリに含めない。
- **Rationale**: claude.ai の機能を使えるのは、Artifact として公開したページだけのため。
